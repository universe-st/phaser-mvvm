# ADR-0004：文本框使用隐藏 DOM `<input>` 镜像桥

- 状态：Accepted
- 日期：2026-09
- 决策来源：PLAN.md §10.1 决策 3、§4.5「TextField 输入桥设计」、§1.2 非目标、§9 风险
- 影响范围：`@phaser-mvvm/widgets` 的 `TextField`/`TextArea`、`@phaser-mvvm/phaser` 的 overlay 层、示例的 Phaser 游戏配置

## 背景

纯 Canvas 文本输入无法获得两样东西：

1. **输入法（IME）候选过程**：中文/日文输入时，候选窗与 `composition*` 事件由浏览器合成，Canvas 上收不到；
2. **移动端软键盘**：软键盘只有在 DOM 元素获得焦点时才会被唤起。

对本项目「工具型表单界面」的定位（PLAN §10.1 决策 4）来说，中文输入是**硬需求**而非增强项；PLAN §9 风险表把它列为「中文表单不可用（对本案是硬需求）」。

## 决策

`TextField` / `TextArea` 采用**隐藏 DOM `<input>`（或 `<textarea>`）镜像桥**，光标与选区仍由框架在 Canvas 内绘制。

### 1. 桥的形态

- 在画布上方、按控件矩形放置一个 `opacity: 0` 的 `<input>`（或 `<textarea>`）；
- 位置由控件矩形推导：每次布局后 + 每帧跟随画布缩放/DPR 变化重新对齐；
- 桥本身**不显示任何视觉**，只负责接收焦点与合成事件。

### 2. 事件与同步

- 监听 `input`、`compositionstart`、`compositionupdate`、`compositionend`、`keydown`、`paste`；
- 值变化同步到 VM 与显示文本；**`compositionstart` → `compositionend` 期间暂停写回 VM**（避免把候选中间态写进数据）；
- 光标/选区由框架在 Canvas 内绘制，保证视觉一致与 z-order 可控；
- 焦点同步：点击控件 → `input.focus()`；失焦 → 提交（`onCommit`）+ 关闭软键盘。

### 3. 前置条件（必须写入使用文档）

- 游戏配置必须开启 `dom.createContainer: true` **并提供 `parent`**；
- 桥的 DOM 节点挂在一个 overlay 容器内；
- **不与 `DOMElement` 控件同层混用**（`DOMElement` 的 z-order 由 Phaser DOM 容器管理，与自建 overlay 会打架）；
- 同一 overlay 容器由 `UIScene` 统一创建/销毁，并与 a11y 镜像层共用（PLAN §10.3「输入桥与 a11y 层」）。

### 4. 降级开关

保留**纯 Canvas 输入模式**作为可选项（`bridge: false`），用于英文/数字表单场景与不支持 DOM 容器的环境。两种模式**共用同一个内部状态机**（光标、选区、编辑命令、校验态），只是事件来源不同。

### 5. 已知局限（写入文档，不隐藏）

- 极端 DPR / 非整数画布缩放下，桥的位置需要校准（光标位置偏差、候选框错位）；
- 屏幕旋转、窗口缩放、`scale` 模式变化时需要重新对齐；
- 无 DOM 容器配置时只能退回纯 Canvas 模式。

## 理由与权衡

- **IME 与软键盘没有替代方案**：让浏览器负责合成，是唯一能同时拿到候选窗与软键盘的路径；自己实现 IME 等于重写一套输入法协议。
- **光标/选区留在 Canvas**：如果连光标也交给 DOM，就需要把 DOM 文本元素的排版与 Canvas 排版对齐，两套排版引擎必然漂移；由框架自己画光标，视觉与 z-order 完全可控（例如光标需要出现在模态遮罩之上）。
- **代价**：
  - 多出一个必须与画布对齐的 DOM 层，成为新的误差来源（PLAN §9 已登记该风险）；
  - 示例工程多了一项「游戏配置必须正确」的前置要求，配置错了表现是「点击无法输入」，对新手不友好 → 需要显式报错提示；
  - 与 `DOMElement` 互斥，限制了混用能力。

## 后果

### 正面

- 中文/日文输入法可用，且候选期间不污染 VM；
- 移动端软键盘可唤起，工具型表单场景成立；
- 剪贴板、键盘导航、`maxLength`、密码掩码等能力可以复用浏览器行为，M5 的实现量显著下降。

### 负面

- M5 验收必须包含**真机手测**（软键盘唤起）与 IME 用例（候选期不写回），无法只靠单元测试覆盖；
- overlay 层的创建/销毁必须严格跟随 `UIScene` 生命周期，否则会出现「场景已销毁但 input 仍在 DOM 中并抢占焦点」的泄漏；
- 纯 Canvas 模式的代码路径需要长期维护（两套事件源），M5 的测试矩阵相应翻倍。
