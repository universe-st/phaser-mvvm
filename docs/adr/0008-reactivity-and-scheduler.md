# ADR-0008：响应式内核与帧对齐调度器

- 状态：Accepted
- 日期：2026-09
- 决策来源：PLAN.md §4.1、§8 性能预算、§9 风险、§1.1 目标 G1
- 影响范围：`@phaser-mvvm/core` 的公开 API 与调度语义、`packages/phaser` 的帧刷新钩子、所有控件的绑定实现

## 背景

MVVM 的收益来自「改数据 → 界面自动更新」，但代价是**更新时机不可控**：一次用户操作可能连续改十几个字段，如果每次赋值都立即触发重排，就会出现「一帧内布局十次」的抖动。

PLAN §9 把该风险登记为「响应式高频写入导致布局抖动 → 掉帧」，§8 则要求「无变化帧布局耗时 = 0」，§1.1 目标 G1 的验收描述是「变更后 UI **在同一帧内批量刷新，无重复布局**」。

同时，框架必须长跑不泄漏：ViewModel 与控件被销毁后，任何残留订阅都会造成内存增长（§9「绑定/effect 泄漏」）。

## 决策

### 1. 响应式 API 面（小写等价 Vue 3）

`ref(v)`、`reactive(obj)`（深度 Proxy）、`computed(fn)`（惰性 + 缓存 + 自动依赖收集）、`watch(source, cb, { immediate, deep, flush })`、`effect(fn)`、`effectScope()`，外加 `ObservableArray/Map/Set`、`makeObservable(instance)`（把类字段转为访问器，供 ViewModel 使用）。

### 2. 依赖清理语义（与 Vue 3 等价）

- `activeEffect` 栈 + 每个 effect 持有 `deps: Set<Dep>`；
- **每次执行前清理失效依赖**，避免条件分支残留订阅导致的「幽灵更新」；
- `watch` 默认按值比较（`Object.is`）短路；`deep: true` 时递归收集。

### 3. 三类刷新时机，UI 默认 `frame`

| flush   | 语义                                            | 用途                                   |
| ------- | ----------------------------------------------- | -------------------------------------- |
| `sync`  | 立即执行                                        | 仅框架内部使用（需要即时一致性的场景） |
| `pre`   | 微任务批量                                      | ViewModel 变更后的普通副作用           |
| `frame` | **UI 默认**：在 Phaser 帧循环的固定点统一 flush | 保证一帧内多次改数据只布局一次         |

- `frame` 由渲染层的 `flushFrame()` 驱动（在一个明确、固定的帧内时机调用一次）；
- 帧内多次写入被合并为一次刷新；
- 布局侧配合脏标记合并（ADR-0002），形成「多次写 → 一次 measure+arrange」。

### 4. `EffectScope` 负责销毁时解绑

- 所有 `effect`/`watch`/`computed` 归入 `EffectScope`；
- `Widget` 持有 `scope: EffectScope`，`destroy()` 时 `scope.stop()`，同时注销输入、归还对象池、断开主题订阅（PLAN §4.3）；
- 页面/场景销毁由 `MVVMPlugin` 在 `SHUTDOWN/DESTROY` 时统一卸载全部页面与绑定（PLAN §4.3）。

### 5. 防环与开发期告警

- **写回短路**：绑定写回前比较当前值，相等则不触发；
- **`trigger` 深度上限** + 开发模式告警（例如在渲染/布局期间写状态、每帧多次布局）；
- ViewModel 约定：普通类 + `makeObservable`，可选 `onMount/onUnmount`、`dispose()`；**不强制继承任何基类**。

## 理由与权衡

- **帧对齐是关键选择**：`pre`（微任务）只能合并同步连续写入；跨 `await` 或动画回调的写入仍会各自触发刷新。UI 的真实约束是「一帧一次」，因此把 flush 点绑到帧循环，语义与真实约束一致。
- **与 Vue 3 语义对齐（小写命名）**：依赖清理、`computed` 惰性缓存、`flush` 三档这些都是被大规模验证的语义，直接对齐可以省掉重新设计与解释成本；小写命名（`ref` 而非 `Ref`）与 Phaser 的代码风格一致。
- **`EffectScope` 而不是手动 `unwatch`**：手动解绑在「控件内嵌控件、列表复用」场景下极易漏；作用域树可以让「销毁一个节点 = 停掉其整棵订阅子树」。
- **代价**：
  - 帧对齐意味着「写完数据立刻读 DOM/布局」不成立（需要显式 flush 或 `nextTick` 语义），使用者需要理解这一点；
  - `reactive` 深度 Proxy 对热路径对象有额外开销，因此热路径（渲染/布局）不读 Proxy，只在绑定层读；
  - `computed` 缓存 + 依赖清理的实现复杂度高，必须有 ≥40 个单测覆盖（PLAN M1 验收）。

## 后果

### 正面

- 一帧内多次数据变更只产生一次布局，直接服务 §8「无变化帧布局耗时 = 0」与 G1 的验收描述。
- 长驻场景（游戏内 HUD）可以通过泄漏测试验证：场景创建→销毁 100 次后 effect 计数回到基线（§7）。
- 因为 UI 刷新与渲染帧解耦，响应式内核不依赖 Phaser，可在 Node 中完整单测（与 ADR-0003 同一思路）。

### 负面

- 「改了数据但界面还没更新」是预期行为，调试时需要提供开发模式的刷新日志/告警，否则会被误判为 bug。
- 帧对齐需要渲染层配合：纯 Node 环境下没有帧循环，测试必须显式调用手动 flush 接口（`flushFrame()` 或等效的同步 flush）。
- 三类 flush 语义若被滥用（例如业务代码大量使用 `sync`）会退化成本 ADR 想避免的抖动，需要在代码评审中约束。
